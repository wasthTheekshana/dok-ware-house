# DOK Warehouse System — Warehouse Expense Tracking (Module 6)

## Context

`docs/WMS_SRS_DOK_Solutions.docx` (WMS-SRS-2026-001) specifies Phase 2 as
"Warehouse Expense Tracking and Staff/Attendance/Payroll" (FR-18 through
FR-26). This module covers the expense-tracking half only
(FR-18/FR-19/FR-20, UC-5) — the smaller, more self-contained piece. The
Staff/Attendance/Payroll half (FR-21–26) is a separate, later module,
since it is substantially larger (staff master, daily attendance, a
monthly payroll approval workflow, and consolidated cross-warehouse payroll
reporting) and depends on this module for nothing.

This module replaces the current manual Excel workbooks — "Warehouse Daily
Expenses – Cost Analysis" and "Warehouse Daily Expense Report" — with a
digital daily-expense entry screen per warehouse, an auto-generated monthly
summary with month-over-month variance, and a cross-warehouse comparison
view for the System Administrator.

This is built entirely on top of the warehouse-scoped RBAC foundation from
Module 5: a new `manage_expenses` permission key, scoped the same way
`manage_box_events` is (whole-router gate plus a `warehouse_admin`'s
`warehouse_ids` filtering every query).

## Decisions

- **One row per warehouse per day.** A `warehouse_expenses` table with a
  `UNIQUE (warehouse_id, expense_date)` constraint holds exactly one entry
  per warehouse per calendar day, matching the SRS's "opens the Daily
  Expense entry screen, pre-filled with today's date" flow (UC-5) —
  re-opening that day's entry edits the existing row, it never creates a
  duplicate.
- **Five fixed categories**, matching FR-18 exactly: Transport/Parking,
  Fuel, Labour, Meals & Refreshments, Other Expenses — each its own amount
  column on the row, not a separate category table or a per-category
  event log. One shared `remarks` field per day (not per category), per
  UC-5's "with a remarks note" (singular).
- **New permission key `manage_expenses`**, granted by role default to
  `warehouse_admin` and `system_admin` only (not `finance_officer` — the
  SRS's role descriptions tie expense entry/oversight to the Warehouse
  Administrator and System Administrator, not Finance). Like Box Events,
  the ENTIRE router (including `GET`) requires this permission — there is
  no separate open-read tier, since no third role needs read-only access
  by default. A `system_admin` can still grant `manage_expenses` to a
  specific `finance_officer` via the existing per-user permission-override
  mechanism (Module 5) if a real need arises.
- **Warehouse scoping matches every other scoped resource**: a
  `warehouse_admin` only sees/writes their own `warehouse_ids`;
  `system_admin` is unscoped. This is what makes FR-20's cross-warehouse
  comparison work for `system_admin` and degrade gracefully (to "compare
  against just yourself") for a `warehouse_admin` who happens to call the
  same endpoint — no special-casing needed.
- **Create/edit are separate operations.** `POST /expenses` creates a new
  day's entry and 409s if one already exists for that warehouse+date
  (enforced by the DB unique constraint); `PUT /expenses/:id` edits an
  existing entry. No immutability lock on past entries — the SRS's
  immutability rule (NFR, line 266) applies only to issued invoices and
  approved payroll, not expenses, so entries stay correctable indefinitely,
  consistent with how Companies/Departments/Box Events already work in
  this app.
- **No historical import.** This module starts empty, tracking only new
  entries going forward — matching how every prior module in this app
  (Box Inventory, Invoicing) also started empty. A one-time Excel import
  can be scoped later if historical workbooks become available.
- **Variance is per-category, not just a grand total.** FR-19 asks for
  "month-over-month variance (value and percentage)" replacing a manual
  SUMMARY sheet that broke costs out by category — the digital replacement
  should preserve that granularity rather than collapsing it to one number.

## Data model

```sql
CREATE TABLE IF NOT EXISTS warehouse_expenses (
    id                 INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id       INTEGER NOT NULL REFERENCES warehouses(id),
    expense_date       DATE NOT NULL,
    transport_amount   NUMERIC(12,2) NOT NULL DEFAULT 0,
    fuel_amount        NUMERIC(12,2) NOT NULL DEFAULT 0,
    labour_amount      NUMERIC(12,2) NOT NULL DEFAULT 0,
    meals_amount       NUMERIC(12,2) NOT NULL DEFAULT 0,
    other_amount       NUMERIC(12,2) NOT NULL DEFAULT 0,
    remarks            TEXT,
    created_by         INTEGER REFERENCES users(id),
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (warehouse_id, expense_date)
);
```

`updated_at` is refreshed on every `PUT`. No `deleted_at`/soft-delete —
this app has no established soft-delete pattern elsewhere (Box Events use
hard `DELETE`), so a hard `DELETE /expenses/:id` is in scope too, gated the
same as create/edit.

## API

- `GET /expenses?warehouse_id=&from=&to=` — list entries. `warehouse_id`
  is optional for `system_admin` (omit for all warehouses); for a
  `warehouse_admin` it is ignored/forced to their own scope. `from`/`to`
  filter `expense_date` inclusively, same convention as Box Events'
  `from`/`to`.
- `POST /expenses` — body: `warehouse_id, expense_date, transport_amount,
  fuel_amount, labour_amount, meals_amount, other_amount, remarks`. 409 if
  a row already exists for that `(warehouse_id, expense_date)`. A
  `warehouse_admin` may only create for their own `warehouse_id` (400 if
  they attempt another).
- `PUT /expenses/:id` — partial update of the amount/remarks fields, same
  scoping as `GET`/`POST` (404 if the entry's warehouse is outside the
  requester's scope, matching the Box Events pattern rather than leaking
  a 403 that would confirm the row's existence).
- `DELETE /expenses/:id` — same scoping/404 behavior.
- `GET /expenses/summary?warehouse_id=&year=&month=` — one warehouse's
  totals for the given month, per category, plus each category's variance
  vs. the prior calendar month (value and percentage). `warehouse_id`
  required for `system_admin` (there's no "all warehouses" summary — that's
  what the comparison endpoint is for); forced to the requester's own
  warehouse for `warehouse_admin`.
- `GET /expenses/comparison?year=&month=` — every warehouse's total for
  the given month, one row per warehouse, for `system_admin`; a
  `warehouse_admin` calling this gets back just their own single-row
  result (same scoping filter as everywhere else, applied to the
  `warehouses` side of the query).
- All five routes sit behind `router.use(authenticateToken);
  router.use(requirePermission('manage_expenses'));`, mirroring
  `boxEventRoutes.ts` exactly.

Variance formula: `(this_month - prior_month)` for value,
`(this_month - prior_month) / prior_month * 100` for percentage — null/N/A
when the prior month has no entry at all (not zero, to distinguish "no
data" from "spent nothing"), matching how a missing baseline should read
as "no comparison available" rather than a misleading "+∞%".

## Frontend

- New nav item "Expenses" in `Layout.tsx`, gated on `manage_expenses` (same
  pattern as the Box Events nav item).
- New page `pages/Expenses.tsx`: a daily-entry form (5 amount inputs +
  remarks, defaulting to today's date and — for `warehouse_admin` — their
  own warehouse; a `system_admin` additionally picks which warehouse), a
  recent-entries table below it with inline edit (mirroring the pattern
  already established in `CompanyDetail.tsx`'s inline price editing), and
  a "Monthly Summary" panel showing the per-category totals + variance for
  the selected warehouse/month, plus (for `system_admin` only) a
  cross-warehouse comparison table.
- Opening the form for a date that already has an entry (checked via
  `GET /expenses?warehouse_id=&from=<date>&to=<date>`) pre-fills it and
  switches the submit action from `POST` to `PUT`, matching UC-5's
  "pre-filled... enters amounts" flow for same-day re-entry.

## Testing

- Backend: standard controller/route test suite following this app's
  established pattern (mocked `execute`, permission-gating tests using the
  real `requirePermission` middleware per the `jest.doMock(...,
  jest.requireActual(...))` pattern this codebase now uses consistently),
  plus warehouse-scoping tests for `GET`/`POST`/`PUT`/`DELETE` mirroring
  Box Events' scoping tests (a `warehouse_admin` outside scope gets
  404/400; `system_admin` is unscoped).
- A pure `computeVariance(current: number | null, prior: number | null):
  {value: number | null, percent: number | null}` helper, TDD'd standalone,
  covering: both present, prior missing (null variance), current zero with
  prior present, current and prior both zero.
- Manual E2E verification against the real database (this app's established
  final-task pattern): create entries as `warehouse_admin`, confirm a
  second `POST` for the same day 409s and `PUT` succeeds instead; confirm
  `system_admin` sees the comparison view across warehouses while
  `warehouse_admin` sees only their own; confirm a `finance_officer`
  (no default `manage_expenses`) gets 403 on every route.
