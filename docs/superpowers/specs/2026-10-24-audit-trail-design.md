# DOK Warehouse System — Audit Trail (FR-30)

## Context

`docs/WMS_SRS_DOK_Solutions.docx` specifies FR-30: "Every create, update or
delete on financial and HR records shall be logged with the acting user, a
timestamp, and before/after values." This is a cross-cutting requirement
that every financial/HR module already shipped this session — Invoices,
Payroll, Warehouse Expenses, Staff, Attendance — currently lacks entirely.

This module is backend-only: a new `audit_log` table, a small logging
helper, and explicit instrumentation of each mutating endpoint in the five
modules named above. A frontend viewer is a natural, separate follow-up
and is explicitly out of scope here — the data needs to exist and be
reliably captured before a UI for browsing it is worth building.

## Decisions

- **Scope is exactly the five modules FR-30 names** — "financial and HR
  records." Invoices, Payroll, Warehouse Expenses, Staff, Attendance.
  Companies, Warehouses, Departments, Box Events, and Users are
  operational/administrative records, not financial or HR records per the
  SRS's own wording, and are explicitly out of scope for this pass.
- **Application-level logging, not DB triggers.** A Postgres trigger
  can't see "which application user made this request" — that's an
  `req.user.id` concept with no natural DB-session equivalent in this
  app's connection-pooled setup. Instead, each mutating controller calls
  a small `logAudit()` helper explicitly, matching this codebase's
  existing style of explicit, readable logic (e.g. the duplicated
  `warehouseScope()` helper, the explicit reversal inserts) over
  implicit magic.
- **The audit write is transactional with the primary write.** Every
  instrumented endpoint wraps its mutation AND its `logAudit()` call in
  the same `withTransaction()` call already used elsewhere in this
  codebase for multi-statement atomic operations (box events, payroll
  reversal). This guarantees the one property that actually matters for
  an audit trail: a mutation can never commit without being logged, and a
  logged entry can never exist for a mutation that didn't commit. Several
  of the instrumented endpoints (`createExpense`, `createStaff`,
  `updateStaff`, `bulkMarkAttendance`) don't currently use
  `withTransaction` and will be converted to as part of this work — this
  is a mechanical wrapping change, not a logic change.
- **One `audit_log` row per affected record**, not one row per request.
  `bulkMarkAttendance` upserts attendance for every staff member in a
  warehouse in one request; it logs one `audit_log` row per staff
  member's attendance record actually created or changed (using that
  attendance row's own `id`), not one row for the whole batch — keeping
  the audit grain consistent with "a record was created/changed," which
  is what FR-30 asks for.
- **`before_value`/`after_value` are full-row JSONB snapshots**, not
  diffs. `before_value` is `NULL` for a `create`; `after_value` is `NULL`
  for a `delete`. For a `reverse` action (Invoices, Payroll — this
  codebase's established immutability pattern inserts a negated mirror
  row rather than mutating the original), `before_value` is the original
  record exactly as it stood before the reversal (unchanged, since
  reversal never touches it) and `after_value` is the newly-inserted
  reversal row — this documents both "what was reversed" and "what the
  reversal looked like" in one entry, rather than needing to cross-
  reference two rows.
- **Who can view it: `system_admin` only, via a direct role check**, not
  a new permission key. Audit logs are sensitive by nature (they expose
  every actor and every historical value across financial/HR data), and
  restricting them to the single most-trusted role avoids the five-
  location permission-key checklist overhead for a read-only,
  system-admin-only endpoint — matching how `isApprover`-style direct
  role checks are already used elsewhere in this codebase (e.g.
  Payroll's approve/reject/reverse) for actions narrower than the
  general permission system.
- **No retention/pruning policy in this pass.** The SRS doesn't specify
  one, row sizes here are small (a few dozen columns of text/numbers per
  snapshot), and this app's data volumes don't currently justify the
  complexity of an archival/pruning job. Noted as a future concern if
  volume ever becomes real.

## Data model

```sql
CREATE TABLE IF NOT EXISTS audit_log (
    id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    table_name    VARCHAR(50) NOT NULL,
    record_id     INTEGER NOT NULL,
    action        VARCHAR(20) NOT NULL CHECK (action IN ('create','update','delete','reverse')),
    actor_id      INTEGER REFERENCES users(id),
    before_value  JSONB,
    after_value   JSONB,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_audit_log_table_record ON audit_log(table_name, record_id);
CREATE INDEX IF NOT EXISTS idx_audit_log_actor ON audit_log(actor_id);
CREATE INDEX IF NOT EXISTS idx_audit_log_created_at ON audit_log(created_at);
```

`table_name` stores the actual DB table name (`invoices`, `payroll`,
`warehouse_expenses`, `staff`, `attendance`) so entries are directly
cross-referenceable. `actor_id` is nullable (matches `created_by`
elsewhere in this app) only for defensive consistency — in practice every
instrumented endpoint sits behind `authenticateToken`, so `req.user.id`
is always present.

## Logging helper

```typescript
// warehouse-server/src/utils/auditLog.ts
export type AuditAction = 'create' | 'update' | 'delete' | 'reverse';

export async function logAudit(
    exec: QueryExecutor, // the `exec` passed into a withTransaction callback
    tableName: string,
    recordId: number,
    action: AuditAction,
    actorId: number | null,
    beforeValue: unknown,
    afterValue: unknown
): Promise<void> {
    await exec(
        `INSERT INTO audit_log (table_name, record_id, action, actor_id, before_value, after_value)
         VALUES (:table_name, :record_id, :action, :actor_id, :before_value, :after_value)`,
        {
            table_name: tableName,
            record_id: recordId,
            action,
            actor_id: actorId,
            before_value: beforeValue == null ? null : JSON.stringify(beforeValue),
            after_value: afterValue == null ? null : JSON.stringify(afterValue),
        }
    );
}
```

`logAudit` takes the transaction's `exec` function (the same callback
signature `withTransaction` already hands to its caller), so the insert
always participates in the caller's transaction — it is a logic error to
call `logAudit` with the module-level `execute` instead of the
transaction's `exec`, and every instrumented call site must use the
transaction form.

## Endpoints instrumented

| Module | Endpoint | Action | before_value | after_value |
|---|---|---|---|---|
| Invoices | `createInvoice` | `create` | `NULL` | the new invoice row |
| Invoices | `reverseInvoice` | `reverse` | the original invoice (unchanged) | the new reversal row |
| Payroll | `createPayroll` | `create` | `NULL` | the new payroll row |
| Payroll | `updatePayroll` | `update` | the row before edit | the row after edit |
| Payroll | `submitPayroll` | `update` | the row before (status=draft/rejected) | the row after (status=pending_approval) |
| Payroll | `approvePayroll` | `update` | the row before (pending_approval) | the row after (approved) |
| Payroll | `rejectPayroll` | `update` | the row before (pending_approval) | the row after (rejected) |
| Payroll | `reversePayroll` | `reverse` | the original payroll (unchanged) | the new reversal row |
| Warehouse Expenses | `createExpense` | `create` | `NULL` | the new expense row |
| Warehouse Expenses | `updateExpense` | `update` | the row before edit | the row after edit |
| Warehouse Expenses | `deleteExpense` | `delete` | the row before delete | `NULL` |
| Staff | `createStaff` | `create` | `NULL` | the new staff row |
| Staff | `updateStaff` | `update` | the row before edit | the row after edit |
| Attendance | `bulkMarkAttendance` | `create` or `update` per row | per-staff-member: `NULL` if no record existed yet for that staff member on that date, else the existing record for that same date before this upsert | the upserted record |

## Read API

```
GET /audit-log?table_name=&record_id=&actor_id=&from=&to=
```

- Behind `authenticateToken`; handler itself checks
  `req.user.role === 'system_admin'`, 403 otherwise (no new permission
  key — see Decisions).
- All query params optional; each adds an `AND` filter to the query,
  matching the filtering pattern already used by `GET /box-events` and
  `GET /expenses`.
- Returns rows ordered `created_at DESC`, capped at the same `LIMIT 500`
  convention `GET /box-events` already uses.
- Joins `users` to include the actor's `username`/`name` in the response
  (so a caller doesn't need a second lookup), matching how
  `getBoxEvents`/`getPayroll` already join in display-friendly fields.

## Testing

- Unit tests for `logAudit()`: confirms the exact SQL/params shape,
  confirms `null` before/after serialize to SQL `NULL` not the JSON
  string `"null"`.
- Controller tests for each instrumented endpoint: confirms
  `withTransaction`'s mocked `exec` receives both the primary
  write and an `INSERT INTO audit_log` call, with the correct
  `action`/`before_value`/`after_value` shape for that endpoint — this
  is the regression net that would catch a future edit to one of these
  controllers accidentally dropping the audit call.
- A transactional-atomicity test (at least one representative endpoint,
  e.g. `createExpense`): confirms that if the simulated `audit_log`
  insert rejects, the primary insert's effects are not observable
  (the mocked transaction wrapper doesn't commit) — proving the
  all-or-nothing guarantee the Decisions section requires, not just
  that both calls were made.
- `GET /audit-log` tests: filter-by-`table_name`, filter-by-`record_id`,
  the `system_admin`-only gate (403 for other roles), and the actor-join
  shape.
- Live E2E (per this session's established pattern): perform one create,
  one update, and one reverse/delete across a couple of the instrumented
  modules against the real database, then query `GET /audit-log` as
  `system_admin` and confirm the logged rows' `before_value`/
  `after_value` match what was actually sent/stored.

## Out of scope (future/separate work)

- A frontend page for browsing the audit trail — this module makes the
  data exist and queryable via API; a dedicated UI is a follow-up.
- Companies, Warehouses, Departments, Box Events, Users — not "financial
  and HR records" per the SRS's own wording; can be added later if a
  broader audit requirement emerges.
- Retention/archival/pruning policy.
- Audit-logging read access (who *viewed* a record) — FR-30 only asks
  for create/update/delete, not reads.
