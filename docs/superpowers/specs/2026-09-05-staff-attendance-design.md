# DOK Warehouse System — Staff Master & Attendance (Module 7)

## Context

`docs/WMS_SRS_DOK_Solutions.docx` (WMS-SRS-2026-001) specifies Phase 2's
second half as "Staff/Attendance/Payroll" (FR-21 through FR-26, UC-6, UC-7).
This module covers the foundational two-thirds — Staff Master (FR-21) and
Attendance (FR-22/FR-23, UC-6) — since Payroll Processing/Approval/Reporting
(FR-24/25/26, UC-7) structurally depends on attendance data existing first
and is scoped as a separate, later module.

This replaces the current manual process of tracking warehouse staff and
daily attendance by hand (no source Excel workbook was named for this in
the SRS's document list, unlike the box/expense modules — this is called
out in the SRS as "new capability beyond what today's spreadsheets do").

This is built entirely on top of the warehouse-scoped RBAC foundation from
Module 5: a new `manage_staff` permission key, scoped the same way
`manage_box_events`/`manage_expenses` are (whole-router gate plus a
`warehouse_admin`'s `warehouse_ids` filtering every query).

## Decisions

- **`manage_staff` covers both Staff Master and Attendance** — one
  permission key, not two. They are tightly coupled (attendance references
  staff records, always used by the same role) and this matches the
  existing precedent of Companies+Departments sharing `manage_companies`.
  Granted by role default to `system_admin` and `warehouse_admin` only, not
  `finance_officer` — matching FR-21's "visible only within that warehouse
  unless viewed by the System Administrator" and the SRS's role
  descriptions, which tie staff/attendance to the Warehouse Administrator
  and System Administrator, not Finance.
- **Staff records are deactivated, never hard-deleted.** A `status`
  column (`active`/`inactive`), matching the existing pattern on
  Companies/Warehouses/Departments/Users. Attendance history (and the
  future Payroll module's history) must survive an employee leaving — a
  hard delete would orphan that history via the FK.
- **Attendance is one row per staff member per day.** A `UNIQUE
  (staff_id, attendance_date)` constraint, matching the
  `warehouse_expenses` table's established one-row-per-day pattern from
  Module 6. Four status values: `present`, `absent`, `half_day`, `leave`,
  with optional `in_time`/`out_time` (only meaningful for `present`/
  `half_day`, but not enforced as mutually exclusive at the DB level —
  the UI conditionally shows them).
- **Daily marking is a single bulk-upsert call**, not one API call per
  staff member. UC-6's flow ("opens Attendance for the current date; the
  system lists all active staff; marks each; saves for the day") is
  naturally one screen action — `POST /attendance/bulk-mark` accepts the
  whole day's entries for a warehouse in one transaction. This also makes
  UC-6's "late correction to a prior day" trivial: it's the same endpoint,
  called again for that date, upserting whichever rows changed.
- **No audit-trail table in this module.** UC-6 mentions a correction
  being "captured in the audit trail," but this app has no audit-trail
  feature yet (that's the SRS's separate, future FR-30). Building a
  one-off `attendance_audit` table now would be scope creep ahead of that
  module's actual design. Attendance stays freely editable — consistent
  with how Box Events and Warehouse Expenses are already editable with no
  audit trail anywhere in this app.
- **No "same month" correction lock in this module.** UC-6 restricts
  corrections to "within the same month," but the only thing that
  actually *closes* a month in the SRS's design is FR-25's payroll
  approval ("payroll prepared... routed to... approval before it is
  treated as final") plus the NFR immutability rule (financial/payroll
  records become immutable once a payroll run is Approved). Since Payroll
  doesn't exist yet, there is nothing to lock against — attendance stays
  fully editable at any time in this module, and the real lock will fall
  out naturally once the Payroll module's approval workflow exists and
  can mark a month's attendance as finalized.
- **System Administrator is unscoped**, matching every other resource in
  this app: sees/manages staff and attendance across all warehouses.

## Data model

```sql
CREATE TABLE IF NOT EXISTS staff (
    id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id  INTEGER NOT NULL REFERENCES warehouses(id),
    name          VARCHAR(200) NOT NULL,
    nic           VARCHAR(20) NOT NULL,
    designation   VARCHAR(100),
    join_date     DATE NOT NULL,
    basic_salary  NUMERIC(12,2) NOT NULL DEFAULT 0,
    epf_no        VARCHAR(50),
    status        VARCHAR(20) NOT NULL DEFAULT 'active' CHECK (status IN ('active','inactive')),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS attendance (
    id                INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    staff_id          INTEGER NOT NULL REFERENCES staff(id),
    attendance_date   DATE NOT NULL,
    status            VARCHAR(20) NOT NULL CHECK (status IN ('present','absent','half_day','leave')),
    in_time           TIME,
    out_time          TIME,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (staff_id, attendance_date)
);
```

`nic` (National Identity Card number) is not UNIQUE at the DB level —
the SRS doesn't call for cross-warehouse uniqueness enforcement, and two
different people could theoretically share a data-entry NIC typo that
shouldn't hard-block save; this mirrors how `code` fields elsewhere in
this app are unique only where the SRS explicitly requires it.

## API

- `GET /staff?warehouse_id=&status=` — list, warehouse-scoped for
  `warehouse_admin`, optional cross-warehouse filter for `system_admin`.
- `POST /staff` — create; a `warehouse_admin` may only create within their
  own scope (400 otherwise, matching the Box Events/Expenses pattern).
- `PUT /staff/:id` — update, including the `status` toggle for
  deactivation; scoped the same way (404 if outside scope, not 403 —
  matching the established "don't confirm existence of an out-of-scope
  resource" convention).
- `POST /attendance/bulk-mark` — body `{ warehouse_id, attendance_date,
  entries: [{staff_id, status, in_time?, out_time?}] }`; upserts every
  entry in one transaction (`INSERT ... ON CONFLICT (staff_id,
  attendance_date) DO UPDATE`); every `staff_id` in `entries` must belong
  to `warehouse_id` and be within the requester's scope, or the whole
  batch is rejected (400) rather than partially applied.
- `GET /attendance?staff_id=&from=&to=` — list/filter, scoped via a join
  back to `staff.warehouse_id`.
- `GET /attendance/summary?staff_id=&year=&month=` — per-status day
  counts for one staff member for one month (FR-23), the same shape a
  future Payroll module's pre-fill will consume.
- All routes behind `router.use(authenticateToken); router.use
  (requirePermission('manage_staff'));`, mirroring `boxEventRoutes.ts`/
  `expenseRoutes.ts` exactly.

## Frontend

- New nav items "Staff" and "Attendance" in `Layout.tsx`, both gated on
  `manage_staff`.
- `pages/Staff.tsx`: a CRUD table (create form + inline edit), mirroring
  `Warehouses.tsx`'s pattern — name, NIC, designation, join date, basic
  salary, EPF number, status toggle. A `system_admin` gets a warehouse
  picker on create; a `warehouse_admin`'s own warehouse is implicit
  (reusing the scoped-picker fix pattern established in Module 6's final
  review).
- `pages/Attendance.tsx`: a date picker (defaults to today) and warehouse
  selection (auto for `warehouse_admin`, picker for `system_admin`, same
  scoped-picker pattern), a table of that warehouse's active staff each
  with a status `<select>` and conditionally-shown in/out time inputs, one
  "Save Day" button that bulk-submits via `/attendance/bulk-mark`. A
  "Monthly Summary" panel below shows per-staff day counts for the
  selected month, laying groundwork the Payroll module will reuse.

## Testing

- Backend: standard controller/route test suite following this app's
  established pattern — mocked `execute`, permission-gating tests using
  the real `requirePermission` middleware, warehouse-scoping tests for
  every staff/attendance endpoint mirroring the Box Events/Expenses
  precedent (a `warehouse_admin` outside scope gets 404/400;
  `system_admin` is unscoped).
- Bulk-mark specifically needs a test proving a batch containing even one
  out-of-scope `staff_id` is rejected in full (no partial writes) — this
  is the one place in this module with meaningfully different transaction
  semantics from prior modules' single-row scoping checks.
- Manual E2E verification against the real database (this app's
  established final-task pattern): create staff as `warehouse_admin`,
  mark a full day's attendance in one save, confirm the monthly summary
  reflects it, confirm a `finance_officer` gets 403 everywhere, confirm
  cross-warehouse isolation for a second `warehouse_admin`.

## Out of scope (this module; future module)

- Payroll Processing, Payroll Approval Workflow, Consolidated Payroll
  Report (FR-24/25/26, UC-7) — the next module, depends on this one's
  attendance summary endpoint.
- Formal audit trail for attendance corrections (deferred to the SRS's
  general FR-30 feature).
- A "same month" correction lock (falls out naturally once Payroll
  Approval exists).
- Historical import — this module starts empty, matching every prior
  module in this app.
